# 附近用餐推荐的实现与验收

交互方法核对：2026-10-21；数据接入路径更新：2026-10-23。本文定义交互与推荐方法；当前完成情况、运行版本和下一步统一维护在本机 `docs/private/STATUS.md`。当前先完成聊天体验，菜单扩充与外部食品数据接入随后推进。

## 推荐方法

采用“理解当前条件 → 召回真实候选 → 校验和筛选 → 排序 → 展示与反馈”的流程。结构化服务负责事实与约束，模型负责必要的语义理解和表达。仅有地图店铺时，结果定位为地点候选；具体餐点推荐需要另外的菜单证据。

| 环节 | 本项目采用的方法 | 验收重点 |
|---|---|---|
| 条件理解 | 地点、预算、人数、餐次与本轮排除项分别保存；后续输入只改变明确更新的字段 | 换店和换位置保留预算；找图书馆、超市和维修不触发餐饮 |
| 候选召回 | 高德提供附近店铺，本地已核对菜单和公开来源补充餐点 | 地点 ID、地址与餐点所属店铺能够对应；控制请求次数与缓存有效期 |
| 筛选 | 先检查来源、位置、菜单对应及明确约束，再考虑软性偏好 | 已知超预算应排除；未知价格只作为待核对候选；人均与菜单价分开 |
| 排序 | 小规模试点先用可解释规则：条件符合度、证据完整程度、距离、本轮重复度 | 不把最近等同于最好吃；选择理由能指向已知字段 |
| 展示 | 首轮一个候选，按需展开更多店铺、地址和地图 | 首轮保留距离基准与资料缺项；地图追问准确对应上一轮选择 |
| 反馈 | 区分换一个、当轮拒绝、明确吃过与明确口味偏好 | 排除只影响本轮；推荐过不等于吃过；未确认的偏好不保存 |

## 私聊呈现

首轮由店名、地址、直线距离和实际距离起点帮助用户判断。地图结果附一次来源与菜单、现价、营业状态的缺项说明。

- `吃什么`：配置地图后直接采用明确地点、当前用餐地点或默认校区，给一个地点候选。
- `换一个`：排除上次展示的候选；`多给几个`或`换一批`最多展示三个候选。
- `地图`、`发地图`、`第2家地图`：提供对应店铺的一条地图链接。`地址`只展开地点信息。普通文本通道的链接按需展示；地图卡片需要单独核对客户端兼容性。
- `15元以内`：保存预算；只有 POI 时说明缺少菜单价，不能确认是否够用。后续换店、改地点继续保留预算。
- `再近点`：按更小范围重新查询；仍是同一家时说明没有找到更近的，未知距离不用于证明更近。
- `自己做饭`、`只是想聊聊`等方向更正优先于原用餐任务；相关场景需要继续补齐回放与调度。

保留菜单与价格事实的出处、取得时间和失效规则。来源追问应能定位到具体事实；聊天首轮的显示密度与底层来源保存分别处理。

## 数据与质量目标

1. 先完成一个试点区域：至少五家真实店铺、十个可对应到店铺的餐点。逐项核对组成或规格、口味依据、菜单价格口径和资料时间；缺失字段明确保留未知。
2. 使用来源中的经营类型与餐次筛选候选，覆盖正餐、甜品、饮品的区分。类别未知时不从店名猜测具体在售菜品。
3. 对条件保持、话题更正、无合格候选、价格未知和来源过期分别保留合成回放；开发样本与未参与调整的保留样本分开。
4. 真实 QQ 检查首轮、换店、改预算、再近点、换位置、地图六种交互，记录实际发送内容和耗时；再单独记录用户是否容易选定、是否实际去过及反馈。
5. 先按 [QQ 计划](qq_account_chat_plan.md) 第 13 节完成聊天对象、连续输入、话题纠正、表达和真实评阅，再集中推进试点菜单及数据接入；已有获准资料可先整理，不以食品来源覆盖阻塞聊天体验。

质量按约束遵守、来源覆盖、重复度、选定所需轮数、请求与发送耗时分项观察。离线测试数量、接口成功和用户满意分别记录。

## 美团数据接入

浏览器自动化在技术上可以读取能正常打开的商户与菜单页面，但页面可见、用户已登录或低频访问都不能单独证明具有采集与再展示许可。2026-10-23 核对的 [美团知识产权声明](https://rules-center.meituan.com/m/detail/guize/69) 对未获书面许可的技术抓取作出限制；[门店外卖菜品接口](https://developer.meituan.com/docs/api/rms-pos-api-v2-poi-goods-wmgoods-query) 标注需要业务授权。以下记录平台规则与接入条件，不把技术可行性等同于已获数据权限，也不作个案法律结论。

| 路径 | 接入前提 | 采用范围 |
|---|---|---|
| 官方开放平台 | 按具体业务准入，应用及门店取得所需授权，核对接口、额度和再展示范围 | 优先评估授权门店的菜单/商品同步；不能据此读取任意店铺的完整菜单 |
| 获准的页面采集 | 平台允许该采集方式与用途，明确页面、门店、字段、保存期和展示范围 | 后续先做少量指定店铺验证；登录或安全验证由用户正常完成，遇到访问控制或验证码即暂停，不把绕过方案列为实现依赖 |
| 商家直接提供资料 | 商家提供可使用的原始菜单、价目表或许可范围内的导出文件 | 可按 CSV/JSON 导入设计整理；资料应独立确认来源，不能用商家同意替代平台对其页面采集的许可 |

官方平台存在菜单接口不代表个人开发者可以直接接入全部业务。[连锁品牌接入指引](https://developer.waimai.meituan.com/home/guide/47) 对该接入路径设有准入条件，并注明暂不提供个人开发者对接；具体服务商或其他业务入口须另行核对，不把这一条扩大解释为所有美团业务都不开放。

后续数据源验证先检查以下事项：

1. 每条事实关联具体门店、菜品及规格，保存来源渠道、取得方式、观察/失效时间、允许用途和可见范围。独立记录原价、活动价、会员或优惠券条件；陈旧或缺失的价格保留未知。
2. 区分到店与外卖。单品标价、人均消费、起送门槛、餐盒费、配送费及优惠后的整单实付不是同一口径；不能用一张商品卡片证明本次用餐必定低于预算。
3. 先验证少量指定门店的字段覆盖、更新与失效，再决定是否接入推荐。设置缓存、限频、超时及停止开关；未获准的登录资料不读取、不复制到项目。
4. 当前阶段只保留接入设计，不运行采集、不读取浏览器会话、不请求美团私有接口。聊天体验完成且数据访问范围明确后，再实施对应来源验证。

## 调研来源及采用范围

- [美团：多业务建模在搜索排序中的实践](https://tech.meituan.com/2021/07/08/Multi-Business-Modeling.html)：借鉴数据、召回、排序、展示的分层，以及查询和上下文对候选构成的影响。本项目先使用小规模可解释规则。
- [美团：外卖美食知识图谱的迭代及应用](https://tech.meituan.com/2021/05/27/Food-Knowledge-Graph.html)：借鉴店铺与菜品关联、品类、口味、食材和做法分开表示，以及菜名归一。模型规模与平台数据效果不作为本项目质量证据。
- [美团：餐饮娱乐知识图谱](https://tech.meituan.com/2018/11/22/meituan-brain-nlp-01.html)：借鉴根据用户关心的事实生成推荐理由，并用多个维度刻画候选。
- [高德：搜索 POI 2.0](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch)：官方文档提供经营信息、评分、人均消费和营业时间等可选字段。这些字段的可取得性及时间口径需要逐项核对，人均不证明单品价格。当前实现使用 v3；v5 字段作为后续数据补充的参考，接入前单独验证。

以上采用方案是针对本项目规模与已知问题的工程判断；公开平台的线上效果不外推为 DoraYmon 的效果。
