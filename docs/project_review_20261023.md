## 结论与框架选择

现有插件、服务、存储分层已经可用；消息契约、平台与机器人身份隔离、可注入的适配器/传输、完整轮次存储，以及 FTS5/BM25 权限检索都有实现。继续使用这一框架即可。当前最需要补齐的是消息调度、生成与投递的生命周期、验收门槛，以及真实对话评测。

飞书已复用 QQ 账号的会话编排，说明现有接缝能扩展第二种协议。`services/feishu_sdk.py` 仍明确拒绝创建事件源；安装和验证 SDK、接通事件回调及真实往返是独立的未完成项。不能把“其余层离线通过”写成“飞书已可用”。

当前没有证据表明需要引入微服务、消息中间件、ORM、向量库或新的 Agent 框架。先用受控调度和清楚的领域接口解决已复现问题；后续组件选择由负载与评测决定。

## 建议推进顺序

1. **消息可靠性**：先补调度所有权与阻塞 I/O 边界，再整合投递结果和历史提交。验收应覆盖“慢甲→快乙”、另一会话 `/ping`、清空/更正、首段失败和部分送达。
2. **完整验收语义**：修正必需门槛超时的退出码，并让 CI 执行同一入口；重跑原有门槛和新缺陷回归。
3. **函数与状态整理**：顺着已稳定的链路拆食物流程、配置装配和查询缓存，不按行数机械拆文件。
4. **通道与真实体验**：在飞书 SDK/应用准备就绪后完成真实私聊往返；QQ 用餐多轮、群聊节奏、G0 菜单来源、G2 餐点闭环和 G3 持续运行分别验收。通道接通不自动关闭前述工程缺口。

D2 长期记忆策略、真实数据范围及平台侧准备继续由当前状态文件管理。本次归档不会把未确认方案转换成实施决定。
