## 1. 产品目标与项目组织

QQ 账号分支面向私聊陪伴和小范围群聊，优先做好自然聊天、上下文衔接和日常用餐决策。首个使用场景为江西师范大学瑶湖校区的日常沟通：用户直接说“吃什么”，就能按已配置地点取得附近选择，并用短句继续调整。食物推荐的完整交付是附近真实店铺、具体餐点，以及有依据的内容、份量、口味和价格信息。能力同时供官方 QQ Bot 和 QQ 账号入口使用。

用户操作以自然语言为主，命令保留为可选入口。功能通过对话被触发，回复风格保持连贯；缺少会改变结果的关键信息时才询问。架构选择以实际对话效果、可靠性和维护成本为依据，保留身份隔离、工具事实、任务状态和发送控制等必要职责。

保留同一仓库，共享聊天、食物、检索和存储实现。运行时提供官方 Bot、QQ 账号两个入口，各有连接配置和运行目录。

实施时复用包含现有成果的 WSL 开发检出，先确认分支、提交和已有修改；需要隔离新工作时再创建分支。Windows 检出继续遵守现有沙箱边界。

首个版本的用户体验：

- 私聊可以直接说话；群里被 @、被引用或处于连续对话时能接上话。
- 能理解“附近吃什么”“换一家”“想吃顶饱一点的”“这家有什么值得点”等连续用餐决策。
- 推荐落实到店铺和具体单品、套餐或档口组合，给出位置、餐点内容、份量或规格、口味依据及价格口径。
- 将地图、联网资料和管理员上传的本地店铺/菜单数据结合，保留来源与更新时间。
- 用户可以依据推荐找到店铺或菜单入口，并继续询问距离、吃到什么、是否适合当前这一餐。

首版交付包含 QQ 账号聊天、当前用餐状态、一个试点区域的真实餐点推荐、CSV/JSON 数据导入和本机管理端。账号接通、餐点推荐可用、对外开放分别验收；详细辣度/食材筛选、通用长期记忆、菜单图片识别和外卖报价按后续批次推进。需求已足够启动 P0，QQ 登录和真实位置数据不作为离线开发的前置条件。

当前开发先完成聊天体验：正确接话、连续输入与纠正、自然表达和真实质量评阅，再推进菜单覆盖与完整餐点推荐。已有用餐功能保留回归，避免闲聊被误转为找店；新增食品数据源、管理页面、新模型提供方和飞书 SDK 接入不作为聊天体验的前置条件。共享聊天能力供各入口复用，通道关系和实际验收入口以 STATUS 为准。

## 4. 目标结构和身份边界

```text
官方 QQ Bot ── BotPy 适配 ────┐
                             ├─ 统一消息事件 → 路由与发言策略
QQ 账号 ── NapCat / OneBot ───┘                    │
                                    ┌─────────────┴────────────┐
                                    │ 聊天编排 / 食物推荐服务  │
                                    └─────────────┬────────────┘
                                      上下文、偏好、目录、检索
                                                  │
                                        模型 / 搜索 / 餐厅数据

管理端 ── 配置、数据导入、运行状态与必要操作
```

先在现有分层上扩展，不预先建设通用插件市场或完整 Agent 平台。

- 新消息事件至少包含：平台、机器人账号、会话类型、会话 ID、发言人 ID、消息 ID、时间、文本、@、引用与附件元数据。
- 统一身份使用“平台 + 机器人账号 + 原始用户/群标识”。官方 openid 与普通 QQ 号不能直接视为同一身份，已有私人口味与历史不自动关联。
- 同群的短期公共消息窗口包含发言人、引用对象和时间，只供本群当前对话使用；私聊历史不注入群聊。它与当前按“群 + 用户”保存的个人问答历史是不同数据。
- 第一版群内公共窗口采用有界内存队列，按条数和时间淘汰；消息在触发回复后才按预算选入模型请求。跨重启的群聊记忆另立需求。
- 两入口复用代码和数据格式。独立部署时使用各自运行数据库；公开食物目录可以发布为同一版本的数据包，私有数据不随公开目录同步。
- 插件返回业务结果，由发送层适配 QQ。客户端、食物服务和模型提示词中不直接散落具体协议调用。

## 5. 聊天优先的行为设计

### 5.1 发言判断

支持普通私聊、@、引用机器人和正在进行的连续对话。按用户 2026-10-23 的选择，QQ 普通群消息默认按内容选择性接话；群列表有值时保留指定范围。关闭普通参与的配置和封闭名单模式继续保留，真实群聊验收单独记录。

处理顺序：访问范围与静默检查 → 忽略自身/重复事件 → 判断是否对机器人说话 → 合并连续消息 → 生成或调用食物服务 → 再检查会话版本与静默状态 → 发送。

- 群内普通消息不要求逐条调用模型；先用 @、引用、关键词、连续对话和冷却规则筛选，确有需要时再做轻量语义判断。
- 同一会话串行处理业务状态，不同会话可以独立运行。模型和搜索请求不能阻塞全部群消息接收。
- 引用和多人发言必须保留发言人，不能把甲的预算当作乙的要求。
- 普通插话设置群级冷却与频率上限；初始可从 30 秒冷却、每分钟最多 2 次自动参与试用，直接 @ 另设受控优先级。这些是待观察调整的初始参数。
- 允许不回复；不为了维持活跃而重复追问。定时主动发话作为后续按群开启的能力，不在接通账号后默认全开。
- 模型生成期间发生清空、静默或会话重置时，旧回复不得发送或写回新的会话历史。
- “附近有什么”“换一个”等省略表达结合当前话题判断；没有餐饮上下文时，图书馆、超市、维修等需求不能被泛化为找饭吃。
- 群里“没问你”只结束对应的插话或对话分支，不替其他成员关闭整个群的响应。显式 @、引用、连续对话与普通插话分别评价和限流；机器人之间的互相接话也受群级参与预算约束。
- 对同一人的连续输入支持短暂合并；合并等待时长作为试用参数记录。用户更正、取消或结束话题后，检查尚未发送的回复是否仍有效，避免只追求快速抢答。

连续输入仅合并同一平台、机器人、会话和发言人的同一对话分支，保留原消息 ID、顺序和引用对象。引用或接话对象变化时分开处理，其他成员的发言不拼入当前用户请求。实现时先比较不等待与短等待窗口，设置最大等待上限，防止持续补充使回复永远不开始；等待与模型耗时分别记录。清空、静默、取消和局部结束立即处理，不进入合并等待。新输入使尚未发出的旧回复失效时取消旧结果，已经送达的内容按实际投递历史保留。

### 5.2 表达和上下文

- 复用现有人格与上下文编排；普通接话优先一条完整短句，初始试用可从约 5～30 个字符观察。该范围只指导普通群聊表达，不作为硬截断或解释、安慰、代码及功能结果的统一上限。
- 角色感来自轻量、稳定的称呼和语气；保留 DoraYmon 自身人格。能简短回应就自然结束，解释和解决问题时按需要展开，接受用户对语气和篇幅的纠正。
- 长短与用户问题匹配，分段不得破坏代码、列表或用餐选项。确需分两条时，每条承载完整意思；一次生成后按语义拆分，不因分两条而重复调用模型。引用真实消息，不伪造群成员话语。
- 将闲聊、食物决策、知识问答作为可衔接的对话，避免只有斜杠命令才能使用功能。
- 优先修好“换一个”“就这个”“再便宜点”等当前任务内追问，再考虑复杂的人格关系和自主规划。
- 默认先给一个有依据的选择，用户要比较或更多结果时再展开；必要的起点、距离口径、来源与未知项紧随相关结果，避免逐项重复说明。
- 工具是否可用、是否已执行及返回了什么，由本次运行配置和执行结果决定。聊天表达不能将实际可用功能一概说成不会，也不能将未执行的请求说成成功。
- 回复气泡长度与短期历史预算分别管理。缩短输出时仍保留后续追问所需的地点、预算、候选和排除项；现有发送字符与段数上限继续作为保护，调整前核对实际配置。
- 每个待发分段都检查会话有效性与静默状态；某段发送失败后停止后续分段，记录已送达和未送达部分。已发消息不能靠取消旧任务撤回。

普通闲聊、解释求助、情绪回应和工具结果分别评阅。闲聊允许接梗、简短关心或不接话；解释保留必要推理和代码；情绪回应先回应对方正在表达的意思，不强行安慰、建议或连续反问。人物语气不能代替回答内容，也不为追求群友风格虚构经历、关系、群成员原话或工具执行结果。

### 5.2.1 默认地点与自然语言功能

- 地点优先级为本轮明确地点、当前用餐决策地点、允许用于当前场景的显式保存地点、实例默认地点。首个试点默认江西师范大学瑶湖校区；显式保存地点的扩展按既有个人资料边界实施，不顺带决定 D2。
- 首次说“吃什么”“晚饭怎么解决”时，在没有相反要求的情况下直接进入默认地点附近的查询。首次使用或起点变化时在结果中顺带说明查询区域；实际解析到校门时，距离按该起点表达，不声称获取了用户实时定位。
- “自己做饭”“帮我想菜”等明确要求优先；情绪表达或话题更正可以结束当前用餐分支，不因含有餐饮词就强制调用地图。
- 规则处理明确请求；歧义结合上下文消解，必要时只问一个关键问题。语义判断与回复生成按需要复用现有调用，避免每条消息固定多次模型请求。
- 当前地点或菜单来源不足时，给出可用结果并明确缺项；只有 POI 时可提供附近店铺及地图入口，不能宣称已完成具体餐点、预算或口味筛选。

### 5.3 模型配置

首轮候选为百炼普通按量 API 的 `qwen3.7-flash` 和 DeepSeek Flash。两个候选先比较显式非思考模式，再按需要增加 DeepSeek 的 `low` 对照；实施时核对实际可用模型 ID、快照版本与参数。依据同批样本的聊天自然度、条件保留、工具结果使用、延迟和费用确定默认模型，当前不预定性能胜者。

模型配置分别保存提供方、模型 ID、接口地址、密钥环境变量名、思考设置、上下文预算、输出长度和超时。思考开关与档位按提供方文档转换，不能把同名参数直接视为等价；不以回复中是否显示思考内容判断请求配置。对话和摘要可分别配置模型，记录实际调用次数、用量、延迟和错误，缺失的用量保留未知。复杂解释是否升级模型在真实评测后确定。

模型接入先保留现有 DeepSeek 调用兼容，再增加百炼适配，不同时重写聊天和 RAG 编排。地图与搜索使用独立接口，聊天模型是否自带联网功能不影响附近推荐服务的职责。

后端调用使用允许用于自定义应用的 API。百炼 Coding Plan 和 Token Plan 个人版的套餐 Key 不用于本 QQ 后端；开通订阅不代表按量 API 调用可抵扣套餐额度。接入前依据 [Qwen3.7 Flash 模型文档](https://help.aliyun.com/zh/model-studio/qwen3-7-flash)、[Coding Plan 说明](https://help.aliyun.com/zh/model-studio/coding-plan)及 [Token Plan 个人版说明](https://help.aliyun.com/zh/model-studio/token-plan-personal-overview)复核模型、计费入口与适用范围。计划不固定易变化的价格和套餐模型名单。

### 5.4 上下文与个性化

短期对话上下文、当前用餐状态和跨会话个人偏好分别管理，各自有明确用途。

| 层级 | 当前实现 | 推进方式 |
|---|---|---|
| 短期对话上下文 | 已有完整问答轮次、后台摘要、过期和清空 | 首版复用；修复在途回复与清空的竞争，适配 QQ 账号身份和群内发言人 |
| 当前用餐状态 | 食物插件会写入问答历史，但推荐调用只接收本轮文本和保存的口味，没有独立任务状态 | 首版新增结构化状态，可靠处理“换一家”“再近点”“还是刚才那个” |
| 轻量个人偏好 | 已有明确保存、查看和删除口味文本的命令 | 首版沿用；附近推荐有效后，建议扩展常用区域、预算、份量和明确店铺反馈，并提供查看、修改和删除 |
| 通用长期个人记忆 | 只有数据类型预留，尚未接通通用存储和读写策略 | 写入方式继续等待 D2 决定，自动抽取与更广泛个人资料不作为首版依赖 |

当前用餐状态至少保存起点和范围、本轮预算/人数、候选店铺与餐点 ID、当前首推、已排除选项和原因、资料来源及有效时间。每次追问只修改相关字段；改变位置要重新检索附近候选，不能继续使用原区域的结果。

用餐状态按平台、机器人账号、私聊或群、发言人隔离；首版采用有界会话缓存，重启后失效，超时可配置。结束本次决策、重置、清空或超时后失效。最近被排除的店铺只影响当前决策，不自动变成用户永久不喜欢的店铺。推荐过也不代表吃过。

个人偏好的适用顺序为当前明确需求优先，其次才是允许在当前场景使用的已保存偏好。精确实时位置作为本轮状态处理；常用区域等跨会话信息的保存方式属于待确定的个人记忆策略。群聊只能使用该群当前可见的信息和明确允许用于群聊的个人资料。

轻量记忆用于减少重复询问、调整排序和聊天表达；店铺、菜单、份量和口味的事实依据仍由真实来源提供。无需先建设向量记忆库或关系图才能完成这些功能。

## 6. 共享附近用餐推荐

### 6.1 推荐结果

一个可用选择由“附近真实店铺 + 具体餐点 + 餐点内容和口味依据”组成。首先帮助用户决定去哪里、点什么，以及这一份能吃到什么。默认先给一个最合适的选择，用户不满意时再换。

首推结果至少包含：

- 店铺或档口名称、地址或地图入口，以及相对用户起点的距离或步行时间；说明采用直线距离还是路线结果。
- 这家店有来源支持的单品、套餐或餐点组合，不能只从店名推断它卖什么。
- 套餐组成、份量或规格，足以初步判断适不适合当前这一餐；具体重量、数量或“够几人吃”需要来源，不能由模型补写。
- 有信息量的口味描述，例如做法、风味、汤底或口感，并区分商家介绍、顾客评价和用户反馈。详细辣度与食材筛选在后续完善。
- 能取得的菜单价格或价格区间、计价口径、来源和更新时间。用户提出预算时，未知菜价或店铺人均不能证明该餐点符合预算。

餐点组成、份量和规格帮助用户判断这一份是否适合当前这一餐。是否顶饱、口味是否合适需要通过有来源的描述和实际反馈判断，不能仅凭菜名给结论。

在菜单补齐前，可先交付真实附近店铺查询。默认给一个距离等依据明确的候选、地址和实际距离起点；地图、导航或地址追问展开对应店铺信息，更多候选按需提供。更完整的菜单、价格与用餐建议按数据覆盖逐步补充。该可用阶段与第 11 节 G2 的完整餐点闭环分别验收。分层推荐方法、按需展示与数据目标见 [用餐推荐设计](food_recommendation_design.md)。

美团菜单与价格暂列后续数据源评估，接入条件及价格口径见用餐推荐设计中的“美团数据接入”。当前不依赖未获许可的采集，也不以浏览器能看到页面证明已经获得批量获取和再展示数据的许可。

### 6.2 数据职责

地图提供位置和店铺候选，菜单与公开资料提供具体餐点，结构化服务校验与排序，模型组织自然回复。

| 数据 | 最小字段与用途 |
|---|---|
| 推荐位置 | 用户明确地点、当前决策地点或实例默认地点，可接受范围与取得时间；三者均不可用时才询问起点 |
| 店铺/档口 | 稳定来源 ID、名称、地址、坐标或地图链接、营业相关信息及来源时间；营业状态未知时保留未知 |
| 餐点 | 店铺 ID、具体单品/套餐名、组成、份量/规格、适用餐次和证据链接，组成与份量允许分别来自不同记录 |
| 口味说明 | 做法、风味和口感描述，及其来自菜单、商家、评价或明确反馈的来源类型和时间 |
| 价格记录 | 金额或区间、币种、按份/按人、菜单价/人均/估算、采集时间和来源；不把未知值写成 0 |
| 当前用餐会话 | 当前起点/范围、预算、人数、候选及首推店铺/餐点 ID、已排除项及原因、来源与有效时间，支持局部条件更新和决策失效 |
| 推荐反馈 | 推荐、拒绝、收藏和明确“吃过”分别记录；不能把推荐过自动当作吃过 |
| 资料范围 | 来源文件或链接、导入批次、更新时间、用户/群/公共可见范围 |

现有口味偏好可继续使用；首版先做好口味描述和基本选择，细粒度辣度、食材及营养字段随后续需求扩展。用户已明确的忌口仍须遵守；证据不足时不能宣称符合该限制。

### 6.3 一轮推荐流程

1. 按第 5.2.1 节选取起点，优先接受明确的学校、商圈或地标。没有明确地点时使用当前决策或实例默认地点；用户明确改到另一个城市时继续缩小区域，不沿用旧校区或把全城结果当作附近。
2. 合并用户本轮明确提供的预算、人数和用餐需求；没有必要就不先询问辣度、食材等细项。
3. 查询附近真实店铺，结合本地已核对菜单或联网资料，形成具体店铺与餐点的关联候选。
4. 校验餐点存在的证据、组成/份量、口味描述、价格口径与更新时间；只有 POI 或泛泛菜名的记录继续作为待补充候选。
5. 优先按真实性、可达性、餐点内容与口味信息是否充分筛选，再结合预算、当前场景和近期推荐重复度排序。
6. 给出一个有依据的首推和前往/查看入口；支持“换一家”“分量大一点”“再近点”“这家具体有什么”等追问，保留当前位置与条件。
7. 网络失败时可使用仍有来源和时间标记的本地附近记录；没有合格候选时说明缺少哪类资料，不用样例菜名填充真实推荐。

第一轮先在一个学校或商圈建立有来源的小规模店铺与菜单集合，检查“店铺能找到、餐点有依据、内容与口味足够具体”。来源覆盖率通过后再扩展地区。

### 6.4 上传数据

上传优先服务真实附近选择：店铺/档口位置、实际菜单、套餐组成、份量或规格、口味资料、价格和来源时间。

首版先有能验证推荐的最小 CSV/JSON 导入，再完善通用上传管理。随后支持 XLSX、多工作表映射及 PDF/菜单截图识别；识别结果先生成草稿，核对店名、餐点、组成、份量/单位和价格后发布。普通菜谱文档作为后续用途接入。

先提供管理端上传入口，随后接 QQ 私聊文件，两入口使用同一导入流程：上传 → 映射/识别 → 预览有效和错误行 → 确认可见范围 → 发布批次。按文件和记录标识去重，支持按批次回滚与删除；删除后更新关联索引。

每条资料保留来源文件/链接、导入者、批次、更新时间和可见范围。默认归上传者可见，向群或公共目录发布须有相应权限。现有私人资料不会因新增目录而扩大可见范围。

上传的表格、文档和网页仅作为资料，里面的指令不能更改系统规则或触发管理动作。解析时限制格式、体积和行数，不执行表格公式或宏。

## 7. 首版位置与联网数据

位置、真实店铺查询和餐点资料核实属于附近推荐的首版依赖。可以直接调用独立地图和搜索服务，不要求先实现通用 Agent。

[高德 POI 搜索](https://lbs.amap.com/api/webservice/guide/api-advanced/search)提供关键词和周边搜索，可作为店铺位置来源；部分餐饮 POI 可带人均消费等字段。POI 用于查找店铺，具体卖什么、套餐组成、份量和口味还需要菜单或其他对应资料。

已核对 [DeepSeek Search API](https://api-docs.deepseek.com/api/search/)：可返回标题、链接、摘要、正文和时间等结构化结果，可评测用于查找店铺菜单、餐点和评价线索。网页读取可参考其 [Fetch API](https://api-docs.deepseek.com/api/fetch/)。需要验证实际可访问来源对目标地区的覆盖，不能因搜索接口有结果就认定推荐合格。

搜索查询只包含必要的店铺、餐点和用户提供的地区，不发送整段聊天历史或私人资料。初始每轮最多 2 次搜索和 2 个网页读取，统一超时、缓存和费用上限；预算用尽仍缺证据时停止补全并说明缺项。

每条事实保留具体来源与查询时间。网页摘要不能覆盖上传菜单的已核对字段；信息冲突时保留各自口径和时间，不拼成一个确定答案。已有 `/知识问` 的本地来源与拒答语义继续保留。

店铺存在、当前营业、餐点在售和支持外卖是不同事实，分别按取得的证据表达。地图中的人均消费不能替代餐点售价，也不能证明实时库存、配送范围或到手价。

## 8. 后续增强

附近推荐稳定后，再按以下内容扩展：

1. 扩大店铺和菜单覆盖，完善上传、更新、过期检查与用户实际反馈。
2. 细化辣度、食材、制作方式、忌口和个人偏好筛选；保留当前要求与普通长期偏好的优先关系。
3. 对接能取得有效数据的菜单与外卖入口，展示可核实的在售、配送和价格信息；具体报价接口需核对授权与字段。
4. 支持“在家怎么做”、已有食材和菜谱检索，复用现有 FTS5/BM25；是否增加向量检索由召回评测决定。

份量、价格、食材或口味资料缺失时保留未知，不由模型生成后当作已核实事实。

## 10. 开发批次与依赖

### 11.1 离线验证

每个连贯代码批次运行受影响测试；共享消息、存储、路由或模型接口改动后运行现有全量离线测试：

```bash
.venv/bin/python -m unittest discover -s tests -t .
```

测试使用临时数据库、合成消息和 mock QQ/模型/地图/搜索。历史记录中的 183 项通过只是已有基线，实施时记录实际测试结果，不将其当作新增批次通过证明。涉及 RAG 时沿用既有离线评测入口和已定门槛，不重复扩建相同评测工具。

必须覆盖的行为：

- 聊天：单人多轮、多人插话、引用、非对机器人发言、静默、重复事件、自身消息、断线重连、超时和生成中清空。
- 用餐：缺位置、同名异地店铺、仅有 POI、内容/份量缺失、空泛口味、过期菜单、人均误作餐点价、未知价格与预算、换一家、修改单一条件、换位置、多人隔离和来源冲突。

硬性要求为零跨身份资料泄漏、零无来源的店铺/餐点/实时报价、清空后旧结果不回写，以及不把用户明确限制忽略或误报为已满足。硬性要求未通过时不能用平均质量分抵消。

### 11.3 对话体验回放

从已授权参考对话提取交互模式，改写为 20～30 组合成多轮场景；固定开发组与未参与提示词调整的保留组。保留发言人、时间间隔、@、引用、连续输入和话题变化等结构，替换身份、原话和群内私事。离线测试直接读取合成样本，不读取原始聊天文件、真实数据库或私人资料；原始群聊不提交、不作为知识库或长期记忆自动导入。

| 场景 | 应观察的行为 |
|---|---|
| 日常接话、接梗、解释 | 简单回应可以自然结束；解释完整，长度随目的变化，角色语气不挤占信息 |
| 多人插话与引用 | 确认对谁说话、接哪条消息；“没问你”结束对应分支，其他人的直接请求仍可响应 |
| 语气纠正与结束话题 | 直接调整表达；取消、撤回或更正后不继续发送过时内容 |
| 连续输入与分段 | 合并同一人的补充；按完整意思分段；首段失败停止后续，送达结果可核对 |
| 默认地区用餐 | “吃什么”直接得到默认区域的真实候选；明确换位置覆盖默认值，做饭或陪聊要求不被强转地图 |
| 用餐追问与歧义 | 换一家、近点、改预算保留未改条件；非餐饮附近需求不误触发；价格未知时不报已满足预算 |

自动回放验证路由、状态、隔离和发送行为；真实模型自然度另行人工评阅。记录额外澄清轮数、条件重复询问、误触发、首个可行动结果的等待时间、气泡数量、无关追问和局部插话频率，保留成功及失败原文。测试数量、关键词覆盖率和全时段发言占比不能单独代替体验结论；某个参考群的长度分布也不作为通用硬指标。

### 11.4 聊天体验的完成条件

| 证据层 | 执行与记录 | 通过条件 |
|---|---|---|
| 合成回放 | 复用 `tests/fixtures/group_dialogues.json` 的固定开发 16 组、保留 8 组；仅在覆盖缺口时补样例，保持两组用途分开 | 明确请求、接话对象、引用、连续补充、取消和隔离满足预期；既有发送失败、限频和历史回归通过；不以新增样例数量代替修复 |
| 真实模型评阅 | 使用合成内容，记录模型实际 ID/版本、思考参数、人格与提示词版本、上下文、工具样本、各次请求用量、耗时和可见回复；失败、无正文及缺失用量单列 | 逐例评价接话是否合适、指代与条件是否正确、表达是否自然、长度是否适合、是否编造事实；影响继续对话的失败修复后重评，未取得真实基线时只报告当前表现 |
| 真实平台往返 | 在获准私聊和测试群验证已加载的代码；覆盖无 @ 求助、@、引用、不同成员、快速补充、话题纠正、局部结束与静默 | 实际送达对象和内容正确；结束后没有旧消息补发；发送失败不冒充已送达；平台观察与模型评阅各有记录，不能由离线通过替代 |

开发组用于定位和调整，保留组用于定稿验证。保留场景一旦用于调参，结果明确标记为已参与调整，不继续将其作为独立的保留效果证明。

预先标注“明确应答”“明确不答”和“存在歧义”三类场景。分别报告明确请求漏答数/应答数、误插话数/不答数；歧义样本单列人工解释。自然度、信息充分性和气泡长度逐例评阅，不用一个平均分抵消跨身份泄漏、错误对象、明确停聊后继续发送或事实编造。

等待性能同时记录首条输入到首个可见回复、最后补充到首个可见回复、合并等待、排队、模型和发送耗时；样本足够时报告 P50/P95，并列出样本量和失败数。比较合并前后每个完成轮次的模型调用次数与用量；短等待不得超过配置上限，不以截断解释或持续取消回答换取较低延迟。

`scripts/eval_chat.py` 可复用作本地路由与回答风格评阅；多人发言时机、引用和连续输入必须经过实际 AccountRunner/会话/群上下文链路。真实评阅前补齐该链路的模型替换、时序输入和上述记录能力，传输仍可使用 fake；这类模型评阅不宣称已经完成 QQ 实发验收。
