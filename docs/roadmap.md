# DoraYmon 路线与阶段计划

更新：2026-10-25（Asia/Shanghai）。路线已采用 MaiBot；当前任务与实测结果只记录在 STATUS.md。

## 路线

聊天主体使用 MaiBot 正式版，QQ 接入采用官方统一 QQ 连接器与现有 NapCat。DoraYmon 自有代码维护用餐领域包、SDK 插件、部署配置与回放评测。只配置上游，不修改其对话引擎源码。

WebUI 负责日常配置与观察；官方 QQ Bot 的 DSH/Codex 电脑控制继续由 Windows computer/qq-agent-bridge 独立维护。

仓库与实例分离，依赖及连接器版本固定。升级前备份整个实例，先在独立实例验证，再安排主号切换。同一 QQ 号只运行一个后端。

## 阶段与验收

完成等级统一使用：离线 → 回放（真实模型、假 QQ）→ QQ 往返 → 持续运行。上一级结果不能替代下一级验收。

### P0 冻结与准备

源码准备已完成：slim 留档，route/maibot 工作树建立，旧工作树和来源快照保留。旧服务进程状态已读检查为 active。NapCat 版本、登录账号和实际名单需在试运行前核对，不从历史记录推定当前值。

新工作树是开发源；Windows QQ 沙箱不承担新路线开发，原服务保留回退。

### P1 封闭试运行

离线准备与 QQ 网关接通已完成，MaiBot 试用服务、管理页和用餐插件已运行，真实试聊已产生模型调用及回复记录。按下列要求继续场景验收，实际状态见 STATUS。

- Python 固定 3.13，MaiBot 固定 1.3.15，官方连接器固定 1.1.8。
- 用 prepare 生成独立实例、应用人设与访问策略、复制自有插件。配置模板不含密钥，账号和名单在本机覆盖目录填写。
- 模型列表固定为一条 deepseek-flash，planner、replyer、utils 共用；模型列表与任务分配保存在仓库覆盖项，升级后 prepare/check 应用并核对。遥测关闭，WebUI 仅监听本机。连接器的主动私聊、戳一戳、撤回、禁言、表情回应和转发工具默认关闭。
- 首轮仅放行操作者私聊。复用现有 NapCat，暂停旧后端及自动检查；已准备试用服务与回退脚本。群验收在明确测试群范围后执行。
- 验收：@ 回复、私聊连续问答、补充消息、停止后让开、其他成员继续提问、重启与断网重连；WebUI 可查看模型调用和 token；24 小时无崩溃。
- 回退：停止候选。若使用主号，恢复旧服务与原运行配置。

### P2 自然度调优与评测

当前有 8 个入门回放场景和通过离线验证的假 NapCat。真实 MaiBot 接入回放台、完整场景移植、真实模型基线和盲评尚未执行。

- 从默认能力与 DoraYmon 人设建立首轮基线；一次只调整一个变量，如自然防抖、开口频率、回复分条或 replyer 模型。
- 将旧版 16 个开发场景和 8 个保留场景移植为带发言人、时间轴和引用关系的回放，保留跨群、私聊/群聊和成员隔离情景。不同评测运行使用干净实例。
- 记录漏答、多答、长度中位数/P90、气泡数和首条延迟。调用次数、token 与费用通过 WebUI 核对；回放台当前未自动采集。
- 嵌入模型就绪并确认范围后启用长期记忆。表达与黑话学习先限定测试范围，每周在 WebUI 查看学习内容。
- 用户盲评约 20 条回复，检查像群友的程度、对象、长度和事实。参考群长度统计只提供方向，不设硬截断。
- 验收：保留组明确应答不漏答，停止后不再插话，事实不编造，盲评优于基线且费用在 D4 预算内。
- 回退：恢复上一版配置及相应实例基线。

### P3 用餐插件

领域包和 SDK 插件已实现餐饮信息整合，真实高德、资料覆盖、模型工具选择与 QQ 往返待验收。新版本未更新运行实例，P1/P2 验收等级不变。

- 自有领域逻辑不依赖宿主；插件只通过 self.ctx 使用宿主能力。
- 提供 nearby_food 和 meal_export 工具，支持起点、口味与场景要求、预算记录、换店、近一点、停止、地图和同一快照的三种文件导出。用餐状态按聊天流和可核实的成员 ID 隔离，默认 30 分钟过期。
- 店名、地址、直线距离只来自高德。无菜单证据时不宣称预算满足；地点有歧义或查询失败时说明并请求可用信息。
- 地图链接由工具直接发送并检查平台最终消息 ID；未确认时不自动重发。
- 验收：测试群完成“吃什么、换一个、15元以内、近一点、换到某地附近、地图”；同名成员不会共享条件；回复逐条对应工具事实。
- 当前记录并传递用户明确提出的口味与场景要求；长期口味档案、签到与自研知识检索暂不迁移，先评估 MaiBot 自带能力的缺口。
- 回退：在 WebUI 禁用用餐插件，聊天保持可用。

#### 餐饮信息与数据来源

公开文档核对：2026-10-25。已实现商家 JSON、小红书与点评只读 MCP 适配及统一导出，实际服务未配置、外部覆盖未验收。以下信息需求和真实数据验证仍为进入条件，P1/P2 按实际证据验收。

推荐目标是帮助用户了解附近可以吃什么、各候选有什么特点，以及是否适合本次需求。先评估菜单、菜品特征和用餐体验的信息覆盖，再选择接入渠道。高德继续负责地点与路线；餐点与体验需要逐项补足证据。价格作为信息维度保留，用户明确预算时检查约束。

| 信息 | 支持的判断 | 证据要求 |
|---|---|---|
| 门店与可达性 | 具体是哪家分店、在哪里、如何到达 | 高德地点 ID、地址与距离口径；步行时间须有路线结果 |
| 餐点与口味 | 有哪些菜、食材与做法、辣度、规格与分量 | 可对应分店的菜单、商家说明或原始资料；不从店名或菜系推定实际供应和可定制程度 |
| 用餐场景 | 营业时段、堂食/外卖、环境、独食或聚餐、排队与出餐情况 | 商家资料、带时间的现场信息或可核验评价；营业时间不等于当下营业，历史体验不作实时保证 |
| 体验与差异 | 哪些菜常被提及、口味和服务评价、适合谁及有哪些取舍 | 保存评价出处与时间，区分个人感受和经营事实，呈现具体依据与意见差异；评分和销量不能替代体验说明 |
| 消费条件 | 单品或套餐价格、人数、预约和使用限制 | 标明资料日期、规格与价格口径；外卖另核配送、包装、起送与个人优惠，未知价格不证明预算满足 |

每项信息记录来源与观察时间，区分已核实事实、带出处的体验描述和推荐判断。缺项保留未知；推荐理由应能指向具体资料，不能用通用食物知识补写某家店的特色、分量或服务。

| 来源 | 已核对能力 | 适合本项目的用途与限制 |
|---|---|---|
| 高德 Web 服务 v3 | 当前代码使用周边搜索与地理编码；官方文档的 `extensions=all` 另列特色标签、照片、评分、人均消费等可选字段 | 负责地点召回和地图，验证附加字段实际覆盖；不能由 POI 推定完整菜单、当前供应、实际营业状态或用餐体验 |
| 商家原始菜单、介绍与现场资料 | 覆盖取决于逐店获取和核对 | 优先用于小区域的餐点、口味、规格与经营信息试点；按资料日期与来源使用，商家原始资料和采集平台页面的许可分别核对 |
| 美团商家业务接口 | 有门店菜品查询，按业务和门店授权；连锁品牌接入路径另有准入条件 | 适合合作门店的结构化菜单同步，不以此推定个人可查询任意商户 |
| 美团个人导购 Skill | 官网有个人开发者及 MCP/Skills 入口；2026-06-15 发布的官方 Skill 规则明确包含附近商品推荐、选择购买和领券 | 验证其实际返回的信息能否支持餐点与场景判断；官方分发包、MaiBot/WSL 接入和展示范围仍待核对。规则限制未经允许抓取、存储、转发数据，不能直接充当共享餐饮库 |
| 美团联盟商品 API | 官方商品查询提供可推广商品的名称、售价、标签及部分适用范围信息，另有推广取链 | 补充有证据的套餐、规格与使用条件；其商品池不足以承担门店完整菜单、环境和评价资料的主要来源。需获得接口权限并确认缓存和 QQ 展示范围 |

进一步调研美团/大众点评时，重点核对门店详情、菜单、实拍和评价内容的实际可得性及字段覆盖。消费者页面上存在这些信息，不证明开放接口提供相同内容；目前尚未确认个人开发者可自助获取任意门店完整资料的通用路径。通过可访问的商家官网、菜单页或其他原始页面补充信息时，须核实原文、日期与分店归属，搜索摘要只作查找线索。

联盟商品的到店 `availablePoiInfo` 在已读文档中主要列可用门店数量，不能证明某分店适用。接入时仍需核实具体门店与条件；搜索会跨业务召回，需检查返回品类，销量仅代表联盟销量。非官方浏览器 MCP、逆向接口或数据服务需核对来源、允许用途和更新机制；美团知识产权声明对未经许可的技术采集有明确限制。

下一步完成真实信息覆盖与使用范围验证：

1. 在一个常用区域选择至少五家真实店铺、十个餐点。逐店核对菜单、菜品特征、规格与分量、用餐场景、体验依据及消费条件，记录缺项和资料时间。
2. 按上述信息维度比较高德附加字段、商家原始资料、官方接口或 Skill 的覆盖、分店对应、更新与展示条件。根据实际信息价值确定接入顺序，避免用工具数量或商品数量替代有效覆盖。
3. 使用清淡热食、口味偏好、独自快餐、朋友聊天和明确预算等场景验证推荐理由；保留同名分店、资料冲突、过期、缺菜单与超时用例。明确约束先过滤，再按口味和场景匹配、证据质量、距离与重复度选择。
4. 配置经过确认的来源后再进行 QQ 私聊验收。当前适配器只是可调用入口，不代表数据源在线或能获得完整菜单。门店事实、餐点与体验资料分别记录出处；无资料的维度如实保留未知，个人账号结果不跨成员复用。

当前实施边界：高德仍按距离召回并取请求的 1～5 家，再补充这些候选的资料；口味和场景交给 MaiBot 根据引用解释，尚无全区域菜品筛选、自动语义排序或反向从内容发现门店。小红书不读取评论或图片，点评不调用评论；美团官方 Skill、联盟商品和抖音本批未接入。不安装 pi 或第三方采集仓库，不修改 MaiBot 源码。

本地 SQLite 资料库已加入离线实现：按高德地点 ID 保存菜单、结构化餐点/套餐与带时间的来源记录，保留观察历史；获准共享的人工导入资料与成员私有检索分开。查库后对缺项或超期资料补查已配置来源，失败时标记旧记录待复核。既有菜单 JSON 与报告可导入，支持查询、历史和三种导出。真实菜单覆盖和平台近期数据仍待核对；资料库不会替代数据获取、分店验证、菜品匹配或自动推荐排序。

#### 外卖菜单获取路径

2026-10-25 核读官方接口、消费者 H5 入口及以下项目源码，尚未安装或运行第三方采集、读取 Cookie、连接手机或调用真实菜单接口。外卖菜单优先用于餐点、描述、规格和可选项，体验资料继续从带日期的评价补充；字段覆盖以实际返回为准。

建议先按“正常外卖页面只读取样 → 分店对应与字段核对 → 现有 SQLite 私有观察记录”的方式验证 2～3 家具体门店；确认有信息价值后再选择结构化 H5 读取或 APP 读取作为长期入口。对新采集结果默认保留成员范围，先记录菜名、描述、分类、规格、可选口味、观察到的报价与原始商品标识；不从最低价推定全部 SKU 价格，不把无原文的描述扩写为食材或做法。

#### 检索进度提示

长检索已接入聊天中的阶段消息，最终推荐继续由 MaiBot 表达。提示由实际任务事件触发，只有真正开始的检索和已取得的进展才能播报；补资料仅在配置来源后触发，未配置时不展示该阶段。

| 实际阶段 | 消息示例 | 使用条件 |
|---|---|---|
| 查询附近门店 | 正在查你附近的餐厅。 | 提问对象与起点已明确，地图查询正在执行 |
| 补充餐饮信息 | 找到 {候选数} 家候选，正在补充菜品和用餐信息。 | 数量来自实际筛选结果，资料查询确已启动 |
| 整理资料 | 资料找到了，正在整理来源和缺项。 | 已取得补充资料，正在归入对应候选与来源状态 |

初版节奏建议：开始执行约 2 秒仍未完成时发送当前阶段，缓存命中或快速完成直接给结果；后续只在有新增状态、且距上一条至少约 8 秒时更新，一次检索最多 3 条进度消息。阶段变化较快时合并为最新状态，不逐条补发历史阶段，不用定时重复同一句话维持动静。百分比仅在存在可计算的真实总量时采用，默认显示阶段。

结束时直接给最终结果，不另加“完成”消息。部分来源失败且已有可核实资料时，说明缺项并提供已取得的信息；全部失败时明确结束查询并提供可用的恢复动作。来源名称仅在确实调用且有助于理解进展时出现。

进度按当前聊天流、提问成员和检索任务归属发送；同一成员明确停止或修改条件导致任务替换时，停止旧任务的提示与结果，其他成员的提问不取消本任务。完成、失败、取消、插件卸载后清理待发送提示，避免最终结果后出现迟到的进度消息。

实现使用插件已有的 `self.ctx.send.text` 能力，检索状态由实际执行流程提供，不修改 MaiBot 对话引擎。进度发送不设置 `stop_after_execution`，不截断最终回复；按 SDK 的发送确认记录结果，发送未确认不自动重发，提示失败不阻断正常检索和最终结果。发送和取消行为需核对锁定宿主的实际执行时序。

离线验证使用合成消息与服务替身，覆盖快速完成、慢检索、阶段合并、部分失败、停止与替换、跨成员/聊天流、发送未确认及结果后的提示清理。真实私聊仍需检查宿主工具调度、实际消息数量、顺序和等待感；不能由插件并发测试推定 QQ 中的即时停止已验收。
